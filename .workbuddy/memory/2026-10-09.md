# 2026-10-09

## Win 系统监控小工具（Tauri + Rust）

从零搭了一个 Windows 桌面监控工具，监控 CPU / 内存 / 硬盘 / 电池 / 适配充电功率。

- 技术栈：Tauri 2.12.1 + Rust 1.97 (msvc) + Vite 7 + 原生 JS（无图表库，canvas 手绘）
- 已在真机编译验证：产出 `src-tauri/target/release/win-monitor.exe`（3.2 MB）与 NSIS 安装包（1.1 MB）
- 依赖选型定稿：sysinfo 0.39.6、windows-sys 0.59（只需 Win32_Foundation / Win32_System_Power / Win32_System_SystemInformation）

### 关键设计

- Rust 侧后台采样线程每 N ms 刷新一次，前端只取最后一次快照；避免多窗口重复采样
- 磁盘 Read/Write 速率用 sysinfo `Disk::usage()` 的增量 ÷ **实测采样间隔**（不用理论间隔，抗抖动）
- 已提交内存用 `GlobalMemoryStatusEx` 补齐 sysinfo 没有的 commit 数据
- 电池 + 充放电功率用 `CallNtPowerInformation(SystemBatteryState)`，`GetSystemPowerStatus` 作降级

### 踩坑记录（重要）

1. **`SYSTEM_BATTERY_STATE::Rate` 是有符号的**：文档写 DWORD，实机返回 `0xFFFFFCB8` = **-840**（负值=放电 mW，正值=充电 mW）。按无符号读会得出「4294966 W」这种荒谬值。已在 `win32::decode_rate` 统一按符号解方向。
2. Windows 惯用 `0xFFFFFFFF` 表示字段无效（MaxCapacity / EstimatedTime 等），必须在 FFI 边界过滤，否则变成 4.29 MWh。
3. sysinfo 0.39 的 `Pid` 不支持 Deref，要用 `p.pid().as_u32()`。
4. tauri-build 缺 icons/icon.ico 会直接构建失败，已用 `tools/make_icons.py`（Pillow）生成。
5. Vite 构建目标为 safari13 时不支持 top-level await，改用 `tick().then(schedule)`。
6. **同一文件的多个 Edit 并行下发会互相覆盖丢失**，同文件修改必须串行。

### 二阶段踩坑（重要）

1. **WMI `0x80041003` (WBEM_E_ACCESS_DENIED)**：需对 `IWbemServices` 调 `CoSetProxyBlanket`（`RPC_C_AUTHN_LEVEL_CALL` + `RPC_C_IMP_LEVEL_IMPERSONATE`）。`EOAC_DEFAULT` 对 `CoInitializeSecurity` 非法，改用 `EOAC_NONE`。
2. **PDH 堆损坏**：`PdhGetFormattedCounterArrayW` 必须把实际缓冲区大小回传（`size` 出参），否则下一次调用越界写堆。
3. **NVML DLL 卸载崩溃**：`Nvml` 实例要长期持有（进程级），不能每次采样 init/drop。
4. **网络重复计数**：同一物理网卡会出现真实接口 + NDIS 过滤驱动两条记录，按 MAC / 累计流量相同去重，否则汇总速率翻倍。
5. mudata 0.20 的 `MenuBuilder` 方法名与旧版不同，按实际 API 调整。

## 第三阶段：UI 布局 Bug（本轮修复）

**现象**：真机窗口（1240×820）里卡片内容溢出卡片边框、上下行互相叠压（"适配充电功率"数值压到"CPU 占用趋势"上）。

**根因（实测定位，非猜测）**：注入探针量得 `grid.clientHeight == grid.scrollHeight == 621`、
隐式行被均摊成 5×111.8px，而卡片内容需 128~201px。
即 `#app{height:100vh}` 固定了视口高度，`.grid` 的隐式行被压缩到容器高度，内容溢出卡片（卡片无 `overflow:hidden`）→ 视觉叠压。

**修复**：改为内容决定高度 + 文档纵向滚动。
- `html,body`：`height:100%` → `min-height:100%`，`overflow:hidden` → `overflow-x:hidden; overflow-y:auto`
- `#app`：`height:100vh` → `min-height:100vh`
- `.grid`：`flex:1 1 auto; overflow-y:auto` → `flex:0 0 auto`（去掉内部滚动，交给文档）

**验证方式（可复用）**：真机锁屏时无法截桌面，改用本地静态服务 + Chrome 无头渲染前端（带 `?mock=1`）。
`python -m http.server --directory dist` + `chrome --headless=new --window-size=W,H --screenshot`。
定位布局用「注入探针把 clientHeight/scrollHeight 画到页面上再截图」的办法，比猜 CSS 靠谱。
产物截图：`shots/ui_final.png`（整页）、`shots/ui_window.png`（默认窗口视口）。

## 第四阶段：纵向滚动条缺失（第三阶段的修复不完整，本轮真正修复）

**现象**：真机窗口缺纵向滚动条，下半页内容看不到。

**为什么第三阶段没解决**：那次改成了「`#app{min-height:100vh}` + 文档滚动」，但 `html,body` 仍是
`overflow:hidden`（文档无法滚动）；同时 `.grid{flex:1 1 auto}` 会随 `#app` 一起撑到内容高度，
`overflow-y:auto` 永远不触发 —— 既没有滚动条，超出的内容又被 `overflow:hidden` 裁掉看不见。
（另外：第三阶段那轮有两条 Edit 并行下发到同一个 `style.css`，`#app` 那条被覆盖丢失，
构建产物里实际只有 `.grid` 的 `min-height:0` 生效 —— 再次验证「同文件多 Edit 必须串行」。）

**真正的根因（探针实测）**：`.grid` 是 flex 子项（`min-height:0` + 确定高度），
而 `.card{min-height:0}` 让它作为 grid item 的 **min-content 贡献为 0**；
配合 `.grid` 默认 `align-content:stretch`，5 个隐式行被**均摊拉伸**到刚好填满容器高度
（实测 `rows=111.797px×5`、`grid cli==scr==621`），卡片被压扁、内容溢出卡片边框叠层。

**最终修复（一处最小改动）**：给 `.grid` 加
`grid-auto-rows: max-content;` + `align-content: start;`
—— 行按内容真实高度计算，网格真正溢出并由 `.grid` 自身滚动；
`#app{height:100vh; overflow:hidden}` 固定外壳 → 形成**单一内部滚动条**。

对照实验（在调试页里注入覆盖样式验证，避免反复改源码再重建）：
| 方案 | grid cli/scr | 可滚动 |
| --- | --- | --- |
| `align-content:start` | 621/621 | 否 |
| **`grid-auto-rows:max-content`** | **621/1177** | **是（scrollMoved=556）** |

**经验**：
- flex/grid 里的滚动容器，两个高频坑：① 子项被默认 `stretch` 均摊拉伸；② `overflow` 元素不向父级贡献内在高度。
  用 `grid-auto-rows: max-content` / `align-content: start` 显式控制行尺寸最稳。
- 调试页注入 `join('\n')` 经多层转义（JSON→bash→python）会变成字符串里的**真实换行**，导致 `<script>` 语法错误；
  改用 `innerHTML` + `<br>` 规避。
- 验证 UI：本地静态服务 + Chrome 无头（`--window-size=1240,820`、`?mock=1`），注入探针把
  `grid.clientHeight/scrollHeight`、`scrollMoved` 画到页面上再截图，能定量确认「是否真的溢出且能滚动」。

产物截图：`shots/ui_window.png`（窗口顶部）、`shots/ui_scrolled_bottom.png`（滚到底露出下半页）、`shots/ui_full.png`（整页）。

## 第五阶段：进程 CPU 使用率百分比口径修复

**现象**：进程榜（Top CPU）的百分比看着不对 —— 与全局 CPU 环形图（0–100% 全核合计）量纲不一致，
单进程满载一核时显示 100%，多线程可超 100%，与全局总和对不上，也与任务管理器默认列不一致。

**根因（读 sysinfo 0.39.6 源码 + 实机探测双重确认）**：
- `sysinfo::Process::cpu_usage()` 的 Windows 实现是 `100 * (进程占用/系统总占用) * 逻辑核数`，
  给出**「每核 100%」**口径（单进程跑满一核 = 100%，多线程可超 100%）。
- 而全局 `global_cpu_usage()` 用 PDH `% Idle Time` 算，是**「全核合计 100%」**口径（0–100%）。
- 两者量纲不一致 → 进程榜数字与全局 CPU、任务管理器对不上，表现为「显示不正确」。

**实机探测（examples/proc_probe.rs，已删除）**：本机 `logical_cores = 20`；
空闲时 ZCode 单进程 raw=18.48%，÷20=0.92%；满载时单核进程会是 100%、双核 200%。证实 raw 是每核口径、换算因子须 ÷逻辑核数。

**修复**：
- `sampler.rs::collect_cpu`：取 `let logical_cores_f = cpus.len().max(1) as f32;`，进程 `cpu_usage: p.cpu_usage() / logical_cores_f`（动态核数，不写死）。
- `model.rs::CpuInfo::normalize`：对 `top_cpu` / `top_mem` 的 `cpu_usage` 加 `.clamp(0.0, 100.0)`，防换算抖动/负值越界。
- 换算后：单核满载进程在 20 核机上显示约 5%，所有进程之和 ≈ 全局 CPU，与任务管理器默认列一致。
- README 数据来源表已标注「进程 CPU% 已 ÷逻辑核心数换算成占总算力口径」。

**注意**：若用户其实想要「每核 100%」口径（100% = 跑满一核，多线程可超 100%），则不应除；当前按「与全局一致」口径修复。
前端 `procRows` 无需改动（直接显示 `cpuUsage` 字段）。

## 第六阶段：电源卡片「不论是否插入充电器都不显示功率」修复

**现象**：用户报「适配器的充电功率不论是否插入充电器都不显示」——电源卡片主数值长期显示 `--`。

**根因（实机诊断，非猜测）**：本机电池长期处在「适配器已接入但电池不充不放 / 微放电」状态。
旧代码的 `charge_rate_w` 仅当 `ChargeRate>0`（真充电）时才有值，否则为 `None` → 前端落 `--`。
`probe_battery` 测试打印：`Rate=4294967206`（i32=-90 mW，微放电）、`ChargeRate=0`、`charge_rate_w=None`，坐实根因。
**物理事实**：Windows 不公开适配器额定/输出功率，只公开「电池充放电速率」（SYSTEM_BATTERY_STATE::Rate）。

**修复方案（让任何供电状态都有真实读数）**：
- **主数值（电源功率卡片大数）**：`liveW = chargeRateW ?? dischargeRateW ?? (acOnline ? 0 : null)`。
  已接入但未充电 → 明确给 `0.0`（不再 `--`）；电池供电 → 取放电功率；无电池 → `--`。
- **新增副行「CPU 功耗」**：用 PDH `\Energy Meter(*)\Power`（RAPL，本机实测约 44.9W / 39.2W，单位 mW），
  作为「系统电源相关功耗」的补充读数。`pick_cpu_power` 优先 `*_pkg` 实例，否则取非 `_total` 实例最大值，
  过滤 >1,000,000 mW 异常值。`_total` 实例恒为 0，已避开。
- **卡片改三列**：CPU 功耗 / 电池状态 / 电源（AC 在线）。删除原「放电」列，标题「适配充电功率」→「电源功率」。
- `battery.rs::status_text`：新增 `(_ if info.discharging)` 分支，把「已接入但未充电且微放电」单独表述为
  「适配器已接入，电池未充电（轻微放电）」，保留原「适配器已接入，当前未充电」。

**改动文件**：
- `src-tauri/src/thermal.rs`：`POWER_PATH`、新增 `PdhSample.cpu_power_w`、`pick_cpu_power()`
- `src-tauri/src/model.rs`：`ThermalInfo.cpu_power_w: Option<f32>`
- `src-tauri/src/battery.rs`：`status_text` 新增微放电分支
- `src-tauri/src/lib.rs`：`diag::probe_battery` / `probe_power_counters`（诊断用例，README 已登记）
- `index.html` / `src/main.js` / `public/mock-preview.js`：电源卡片三列 + 新口径
- `README.md`：整体重写，记录「电源功率」「CPU 封装功耗」数据来源与口径

**验证**：
- `cargo check` 通过；`smoke::collect_once` 输出 `cpuPowerW: 39.165695`、`dischargeRateW: 0.6`、
  `statusText: "适配器已接入，电池未充电（轻微放电）"`。
- PDH 速率型计数器需 ≥2 次 collect 且间隔足够（warmup + 1.2s）才出值；单次采样/间隔太近读不到，已确认。

## 副线：逆向 LegionZone 如何取 CPU 温度（用户问询）

目标程序 `C:\Program Files (x86)\Lenovo\LegionZone`（联想 Legion 系列自带工具）。用 Python 字符串提取脚本扫二进制得出结论：

- **主路径（联想机型）**：`LZ2SE.dll` / `LZTrayPlugin.dll` 走联想私有 WMI 提供程序 **`LZWmiX80`**（`root\WMI` 命名空间，源码 `LZBase\wmi\LZWmiX80.cpp`）。
  通过 `WmiHelper::ExecMethod` 调方法 `Query_CAPABILITY_DATA_00/01`，取回 `LENOVO_CAPABILITY_DATA_xx` 数据块，
  内嵌 **"CPU DTS Sensor Temperature"**（Intel 片上数字温度传感器）与 **"Thermistor CPU Sensor Temperature"**（主板热敏电阻）等读数；
  另有 `GetFeatureValue bWmi:%d, ids:0x%x` 按 ID 取单项传感器值。`es-EC`/`quz-EC` 是 EC（嵌入式控制器）命令痕迹。
- **通用回退**：`HardwarePlugin.dll` 含 `SELECT CurrentTemperature From MSAcpi_ThermalZoneTemperature`（`root\WMI`，ACPI 热区，
  deci-Kelvin→℃：`C = K/10 - 273.15`）。
- **GPU 温度**：`ADL_Overdrive5/6_Temperature_Get`（AMD 显卡，AMD Display Library）。
- **本机实证**：`Get-CimInstance root\wmi:MSAcpi_ThermalZoneTemperature` 返回 0 实例，`Win32_TemperatureProbe` 也为空，
  且本机无 `LZWmiX80` 提供程序（当前开发机不是 Legion 机型）→ 证实上面是 LegionZone 在真实机型上的取数路径。
- **对自有工具的启示**：我们项目用 PDH `\Thermal Zone Information(*)\Temperature` + RAPL 取温度/功耗，属通用方案；
  在联想机上可额外尝试 `root\WMI:LZWmiX80` 的 DTS 读数拿更准的 CPU 片上温度（需机型支持）。

## 第七阶段：内置 LibreHardwareMonitor（打包 + 提权拉起 + WMI，不走 Web 服务）

用户实测 `hw` crate 拿不到温度（本机无 OpenHardwareMonitor，0x8004100E = WBEM_E_INVALID_NAMESPACE），
确认 `hw` 只是 OHM 外壳、不新增温度源。决策：**打包 LibreHardwareMonitor（v0.9.6 经典版，.NET Framework 4.7.2）随安装包分发**，
且**只用其 WMI 提供程序**（`root\LibreHardwareMonitor`），**不走 Web 服务（端口 8085）**——与既有 `wmi.rs` 天然契合。

### 实现

- 新增 `src-tauri/src/lhm.rs`：`ensure_lhm_started(resource_dir)` + `kill_lhm(pid)` + 进程管理。
- `src-tauri/resources/lhm/`：41 个 LHM 运行时文件（exe 4.4MB + Lib + 各语言目录 + config），**排除** .cs/.zip/.pdb/.json。
- `tauri.conf.json`：`bundle.resources` 加 `"resources/lhm/": "lhm/"`（Tauri v2 必须显式登记，不会自动打包 `resources/` 目录）。
- `Cargo.toml`：`windows` 加 feature `Win32_UI_Shell` / `Win32_System_Threading` / `Win32_System_Diagnostics_ToolHelp`。
- `lib.rs`：`AppState` 不加字段；改为 `setup` 后台线程调 `ensure_lhm_started`，退出事件 `RunEvent::ExitRequested` 调 `kill_lhm`（用独立 Arc 克隆，避免闭包所有权冲突）。
- `wmi.rs` 早已把 `root\LibreHardwareMonitor` 排在第一优先；`thermal.rs` 多源优先级：LHM/OHM → ACPI-WMI → PDH。

### 运行机制（关键约束，改动前必读）

1. **落盘**：首次复制 `resources/lhm` → `%LOCALAPPDATA%\WinMonitor\lhm`（安装目录只读；LHM 要释放 PawnIO 驱动 + 写配置）。
2. **开 WMI**：`ensure_wmi_enabled` 幂等注入 `<add key="UseWMI" value="true" />` 进 `LibreHardwareMonitor.exe.config`（打包的 config 没有这个键，没有它 `root\LibreHardwareMonitor` 不存在）。
3. **提权拉起**：`ShellExecuteExW` + `runas` + `SW_HIDE`（用 `..Default::default()` 让 nShow=0=SW_HIDE）。读 CPU 核心温度需内核驱动（PawnIO），**必须管理员，首次弹一次 UAC**；用户取消则回退 ACPI/PDH。
4. **进程管理**：LHM 已在运行则不拉起/不杀（防 UAC 轰炸）；仅「本次由我们拉起」才在退出时尝试 `TerminateProcess`。
   **跨完整性级别 kill 大概率失败**（普通权限杀不了提权进程），此时 LHM 继续常驻；下次启动检测到存活直接复用、不再弹 UAC——有意取舍。

### 验证

- `cargo check` 零告警；`cargo build --release` 通过（lto/strip 无问题）。
- `target/release/lhm/` 出现全部 41 个 LHM 文件（含 exe）→ 证明 `bundle.resources` 生效，NSIS 打包会带上。
- 本机缺 makensis，未跑完整 `tauri build` 实际 NSIS 打包；需在装了 NSIS 的机器上 `npm run build` 验证安装包。

## 修复：双击 exe 后窗口显示「localhost 拒绝连接」（ERR_CONNECTION_REFUSED）

## 温度仍取不到：三层根因排查（推翻 LHM-WMI 方案）

- **现象**：UAC 提权通过、页面正常渲染，但温度卡片仍为 `--`，页面底部提示「未检测到可用的温度传感器」。
- **根因 1（决定性）**：**LibreHardwareMonitor 自 v0.9.5 起删除了 WMI 提供程序**。
  逐版本核对 GitHub tree：v0.9.0/0.9.2/0.9.4 有 `LibreHardwareMonitor/WMI/{WmiProvider,Sensor,Hardware,IWmiObject}.cs`，
  v0.9.5 只剩 `TestScripts/basicwmi.py`。0.9.6 源码全文搜索无 `IWbem*`、无 `.mof`、无 `root\LibreHardwareMonitor` 字符串
  （唯一 `UseWMI` 是 `SMBusManager.UseWMI`，管内存 SMBus，不管 WMI 提供程序）。
  → 我们注入的 `UseWMI=true`（已确认写入 `LibreHardwareMonitor.exe.config` 第 14-16 行）是**空操作**，
  `wmi.rs` 的 `hardware_temperatures()` 必然空手而归。
- **根因 2**：0.9.4 的 WMI 走 `System.Management.Instrumentation` 解耦提供程序
  （`[assembly: Instrumented("root/LibreHardwareMonitor")]` + `DefaultManagementProjectInstaller`），
  必须先 `installutil` 注册；且 `Instrumentation.Publish` 的异常被 `catch {}` 静默吞掉 → 极难排查。
- **根因 3（好消息）**：**PawnIO 已安装**（`C:\Program Files\PawnIO\`，20:18，即 LHM 弹框后实际装上了），
  LHM 上次运行落盘的 `LibreHardwareMonitor.config` 里有 **545 个 sensor identifier、其中 90 个温度**
  （含 `/intelcpu/0/temperature/0..14`、`/gpu-nvidia/0/temperature/*`）→ **LHM 确实读到了 CPU 温度，我们只是没通道读它**。
- **0.9.6 仅剩的两个通道**：① `HttpListener`（`runWebServer` + `listenerPort=8085`，本机回环）；
  ② 内置 CSV 日志（`Logger.cs`，`logSensorsMenuItem=true` 打开，写 LHM.exe 同目录、`Append + FileShare.ReadWrite`）。
  ② 不可行：545 列 × 1Hz ≈ 200+ MB/天。
- **用户提出的第三个库 `systemstat` 也不行**：`src/platform/windows/mod.rs:289` 的 `cpu_temp()` 直接
  `Err("Not supported")`，温度只在 Linux/BSD/macOS 实现。连同 `hw`（OHM 外壳）一起，三个库都验证为不可行。
- **已探明的新可行路径（直连 PawnIO 读 MSR）**：协议细节见 `MEMORY.md`「温度数据源」。
  关键点：`\\?\GLOBALROOT\Device\PawnIO` + `IOCTL_PIO_LOAD_BINARY(0x821<<2|41394<<16)`
  + `IOCTL_PIO_EXECUTE_FN(0x841<<2|…)`，执行 `ioctl_read_msr`；Intel 温度 = TjMax(0x1A2) − DTS(0x19C>>16&0x7F)。
  模块 `IntelMSR.bin` 可从 LHM 仓库取（MPL-2.0）。代价：需管理员 → 需自带提权子进程 + 文件交换读数。
- 本机限制：`csc.exe` 在安全黑名单（不能编译 C#），`dotnet` SDK 6.0.301 可用，`sc.exe`/`reg.exe` 被拦。

## 实施：温度改用「PawnIO + Intel MSR」直读（用户选定方案）

- 方案取舍：用户否决 Web 服务；`csc.exe` 被黑名单堵掉「自写 C# 桥接」；0.9.6 又没有 WMI →
  最终选 **纯 Rust 直连 PawnIO 读 MSR**，并把 LHM 整个从安装包移除。
- **新增 `src-tauri/src/pawnio.rs`**：`CreateFileW(\\?\GLOBALROOT\Device\PawnIO)`
  + `IOCTL_PIO_LOAD_BINARY(0x821<<2 | 41394<<16)` 载模块 + `IOCTL_PIO_EXECUTE_FN(0x841<<2|…)` 调
  `ioctl_read_msr`；温度 = TjMax(`0x1A2`) − DTS(`0x1B1` 封装优先 / `0x19C` 逐核兜底，需 `SetThreadAffinityMask`)。
- **新增 `src-tauri/src/msr_bridge.rs`**：主进程普通权限 → 用 `ShellExecuteExW`+`runas`+隐藏窗口
  **拉起自己**（`--pawnio-bridge --module … --out … --parent-pid N`）；子进程每秒写
  `%LOCALAPPDATA%\WinMonitor\pawnio.json`（临时文件 + rename 原子覆盖），并每秒用 `OpenProcess`
  检查父进程存活，**父进程一退自退**——因此不需要跨权限 TerminateProcess。
  一个会话只尝试提权一次（`AtomicBool`），避免 UAC 轰炸；状态文件里带 `parentPid` 以识别上一轮残留。
- **`thermal.rs` 改为 MSR 优先**的四级链：Intel MSR → OHM/旧版 LHM 的 WMI → ACPI 热区(WMI) → PDH；
  MSR 失败原因单独存 `msr_hint` 并在兜底提示里优先展示（更具体：未提权 / 未装 PawnIO / 非 Intel）。
- **移除 LHM**：删除 `src-tauri/resources/lhm`(11MB) 与 `lhm.rs`，`tauri.conf.json` 资源项改为
  `"resources/pawnio/": "pawnio/"`；顺带清理 `target/release/lhm` 与 `%LOCALAPPDATA%\WinMonitor\lhm`。
  **安装包从 6.41 MiB 降到 1.21 MiB**。PawnIO（`C:\Program Files\PawnIO`）保留——本方案依赖它。
- 新增资源 `src-tauri/resources/pawnio/{IntelMSR.bin(4068B), COPYING, README.txt, NOTICE.md}`：
  模块取自 **namazso/PawnIO.Modules v0.1.6 已签名模块（LGPL-2.1）**，签名是 PawnIO 接受它的前提。
- 诊断用例 `diag::lhm_status` → 改为 `diag::pawnio_msr`（打印模块路径、TjMax、封装温度、桥接状态）。
- **关键验证（非提权下跑 `cargo test diag::pawnio_msr`）**：报
  `打开 PawnIO 设备失败…：拒绝访问 (0x80070005)` —— **不是「找不到文件」**，证明
  `\\?\GLOBALROOT\Device\PawnIO` 设备存在、路径与打开参数正确，只差管理员权限。
- **认知修正**：LHM 的 Intel 温度传感器是按 **CPUID 能力位**创建的（`IntelCpu.cs`），
  driver 没通也会列出 `/intelcpu/0/temperature/*`，所以「设置文件里有 15 个温度项」**不能**证明 MSR 读通。
- 收尾状态：`cargo check` 零告警、`npm run build` 成功出包、资源落位 `target/release/pawnio/` 已核对。
  **happy path（提权后模块能否载入、MSR 能否读出）仍需用户在真机点一次 UAC 验证**。

### 追加：PawnIO 改成「随包分发 + 一键安装引导」

用户问「PawnIO 可以直接集成或者引导用户进行安装吗」——答案：**两者都能，且已都做了**。

- **可行性证据（不是猜的）**：
  - LHM 0.9.6 自己就是范例：`MainForm.cs` 把 `PawnIO_setup.exe` 作为 **embedded resource** 内嵌，
    运行时释放到 CWD 再 `Process.Start(path, "-install")`，装完删掉。
  - 安装器自带许可文本就写在二进制里（UTF-16 串）：`All rights reserved.` +
    **`This installer can be redistributed unmodified.`** → 原样分发是明确允许的。
    先例还有 Chocolatey 官方 `pawnio` 包、NWinfo。
  - 安装器 CLI 也是从二进制串里挖出来的：
    `Usage: PawnIOSetup.exe [-install] [-uninstall] [-unrestricted] [-debuginfo] [-silent]`；
    Chocolatey 用的静默参数是 `-install -silent`，validExitCodes `(0, 3010)`。
- **本机 PawnIO 状态（用于验证探测逻辑）**：注册表
  `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\PawnIO` → `DisplayVersion=2.1.0.0`、
  `QuietUninstallString = "C:\Program Files\PawnIO\uninstall.exe" -uninstall -silent`；
  服务 `PawnIO` = Running / Manual。但**代码没有走注册表**——直接 open 设备看失败码更简单可靠。
- **实现**：
  - 新增 `pawnio_setup.rs`：`probe()`（打开设备，`ACCESS_DENIED`=已装 / `FILE_NOT_FOUND`=未装）、
    `run_installer(setup, elevate)`（ShellExecuteExW + NOPASYNC/NOCLOSEPROCESS，等退出取退出码，
    0→Done、3010→RebootRequired、1223→Cancelled）。
  - `resources/pawnio/PawnIO_setup.exe` = 官方 **2.2.0**（3,410,960 B，
    sha256 `1f519a22e47187f70a1379a48ca604981c4fcf694f4e65b734aaa74a9fba3032`，已校验），
    另补 `COPYING-GPL-2.0.txt`（PawnIO 驱动本体许可）并重写 `NOTICE.md` 记录再分发条款。

    `--install-if-missing` 拉起，桥接已是管理员 → 直接跑安装器（`elevate=false`）→ **装+读只弹一次 UAC**。
