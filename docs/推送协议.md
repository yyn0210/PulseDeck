# PulseDeck 数据推送协议（v1）

> 面向设备端作者：DIY 小屏（ESP32 / Arduino）、手机 / 平板 App、树莓派状态屏等，
> 如何接入 PulseDeck 的监控指标推送。协议实现以 `src-tauri/src/push/` 为准，
> 本文档是它的人话版。

## 一句话概览

PulseDeck 在本机开两条**只读单向**的通道（TCP——同一端口同时收裸 TCP 与
WebSocket 客户端，以及 BLE 串口），按用户设置的推送间隔
（300 ms ~ 10 s，默认 1 s）持续吐出同一份紧凑 JSON：

```json
{"schema":1,"tsMs":1760700000000,"sampleIntervalMs":1000,"host":"desktop",
 "cpu":{"usagePct":23.5,"freqMhz":2900,"freqLive":true,"tempC":61.5,"powerW":12.3},
 "mem":{"usagePct":58.3,"usedBytes":9500000000,"totalBytes":17000000000},
 "gpu":{"name":"NVIDIA GeForce RTX 3060 Laptop GPU","usagePct":37,"memPct":44,"tempC":66,"powerW":75.5},
 "bat":{"pct":82,"charging":true,"acOnline":true,"rateW":45.2,"secondsToFull":3600},
 "net":{"downBps":1234567,"upBps":98765,"totalReceivedMiB":12000,"totalTransmittedMiB":2000},
 "disk":{"readBps":300000,"writeBps":1200000},
 "cores":{"load":[12,46,100,3,8,28,67,0]},
 "procs":{"list":[{"name":"pulse-deck.exe","cpuPct":12.5,"memMiB":36}]}}
```

设备**无法**向 PulseDeck 发送任何指令——两条通道都不解析外来字节。没有鉴权：
TCP 只应在可信局域网内开放。

## TCP 通道（NDJSON 与 WebSocket 同端口）

TCP 通道在**同一个端口**（默认 `17432`）上同时收两种客户端：服务端在连接后
约 250 ms 的判定窗口内看首字节——是 HTTP 请求行就走 WebSocket 握手，否则按
裸 TCP（NDJSON）对待。两种客户端收到的 JSON 完全相同，只是帧格式不同。

### 裸 TCP（NDJSON）

1. 在 PulseDeck 设置页「数据推送」里开启 TCP，记下状态行显示的 `局域网IP:端口`
   （默认端口 `17432`）；
2. 设备作为客户端连上去，**连接成功即收到一拍**，之后每个推送间隔收到一拍
   （首拍会因协议判定窗口最多延后 ~250 ms）；
3. 帧格式是 NDJSON：每拍一行 UTF-8 JSON，以 `\n` 结尾；
4. 掉线自动重连即可；服务端从不主动断开空闲连接，但**读取极慢的客户端**
   （写缓冲 1 秒推不下去）会被服务端剔除；
5. 客户端连上后**保持静默**——本协议只收不发，发了的内容也不会被解析。

Python 验收示例：

```python
import socket, json
s = socket.create_connection(("192.168.1.100", 17432))
buf = b""
while True:
    buf += s.recv(4096)
    while b"\n" in buf:
        line, buf = buf.split(b"\n", 1)
        if line.strip():
            d = json.loads(line)
            print(d["cpu"]["usagePct"], d.get("mem", {}).get("usagePct"))
```

### WebSocket

浏览器 / 手机网页**不需要任何原生 App**，一个页面直连：

```js
function connect() {
  const ws = new WebSocket("ws://192.168.1.100:17432/");
  ws.onmessage = (e) => {
    const d = JSON.parse(e.data);   // 与 NDJSON 同一份 JSON（无换行）
    console.log(d.cpu?.usagePct, d.mem?.usagePct);
  };
  ws.onclose = () => setTimeout(connect, 1000); // 慢消费者会被断开，务必重连
}
connect();
```

| 项 | 值 |
| --- | --- |
| URL | `ws://<局域网IP>:17432/`（路径忽略、无子协议；`wss://` 不支持——面向可信局域网） |
| 消息格式 | 每拍**一条 text 消息**，内容 = 同一份 JSON（不带换行） |
| 心跳 | 客户端可发 Ping 帧，服务端自动回 Pong（内容不解析） |
| 断开条件 | 写超时 1 s / 队列积压约 8 拍未消费 / 对端关闭——客户端做好重连即可 |

> WebSocket 与裸 TCP 共用防火墙授权：Windows 首次开启 TCP 弹的授权提示，
> 对两种客户端一视同仁。

> **在哪跑这段代码有讲究**：别在浏览器内部页（`chrome://` / `edge://` 开头，
> 如新标签页、设置页）或带严格 CSP 的网站控制台里执行——那些页面自身的
> `connect-src` 策略会在连接发出前就拦截（报错 "violates the following Content
> Security Policy directive"），与推送服务无关。地址栏打开 `about:blank` 后再开
> 控制台即可；或者直接用仓库自带的验收页 [`tools/push-viewer.html`](../tools/push-viewer.html)
> ——双击用浏览器打开（`file://` 页面没有 CSP 限制），改好地址点「连接」，
> 指标卡片 / 原始 JSON / 断线自动重连都是现成的。

## BLE 通道（Nordic UART Service）

PulseDeck 以标准 NUS 服务广播，广播名 `PulseDeck`。用任何 BLE 串口客户端
（nRF Connect、SerialBluetoothTerminal、ESP32 NimBLE……）连接并**订阅 TX 特征的
notify**，即可收到分帧的数据流。

| 项 | 值 |
| --- | --- |
| 服务 UUID | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| RX 特征（设备→PC，write） | `6e400002-b5a3-f393-e0a9-e50e24dcca9e`（内容被忽略） |
| TX 特征（PC→设备，notify） | `6e400003-b5a3-f393-e0a9-e50e24dcca9e`（数据流） |

### 20 字节安全帧

协商 MTU 在各平台都拿不到，所以按最保守的 20 字节切帧。每帧格式：

```text
[0] idx    本帧序号，0 起
[1] total  本拍载荷共几帧
[2..] data ≤18 字节的载荷切片
```

设备端重组算法（Rust 参考实现在 `push::ble_reassemble`）：

```text
按 total 开一个槽位数组；每收到一帧，校验 idx < total 且帧头的 total 一致，
放进对应槽位；全部槽位填满后按序拼接，得到一拍完整的 UTF-8 JSON，按行解析即可
（BLE 载荷本身不含换行）。任何一帧校验失败就丢弃整拍，等下一拍——
每一拍都自带 (idx, total)，没有跨拍状态。
```

一拍全基础组载荷约 300~500 字节（≈ 20 帧），加上可选的 `cores` / `procs` 组与
电池预估 / 网络累计等增补字段，最坏情况约 1000 字节，1 Hz 下 BLE 完全吃得下；
推送间隔低于 500 ms 时建议减少勾选的指标组。BLE 重组器按 64 帧（≈1152 字节）
封顶设计，全组勾选也留在预算内（后端有按最坏快照断言 <1024 字节的闸门测试）。

## 载荷字段（schema 1）

顶层：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schema` | int | 协议版本，当前恒为 `1`；不认识就别解析 |
| `tsMs` | int | **快照采样时刻**（Unix 毫秒）——是数据年龄，不是设备收到它的时刻 |
| `sampleIntervalMs` | int | 快照的实测采样间隔（毫秒） |
| `host` | string? | 主机名（多台电脑时用于标注），缺省=未取到 |

六个基础指标组**按用户勾选出现**，未勾选的组整组缺席；机器上没有的组也缺席
（无 GPU 不出 `gpu`、无电池不出 `bat`）。组内读不到的字段同样省略（键不存在），
不要假定任何字段必在。

| 组 | 字段 | 说明 |
| --- | --- | --- |
| `cpu` | `usagePct` | 总占用（%，忙时口径，与任务管理器一致） |
| | `freqMhz` | 主频（MHz）。注意键名是 `freqMhz`（serde camelCase，非 `freqMHz`） |
| | `freqLive` | `true` = 实时主频；`false` = 该平台只能给标称频率（基准值） |
| | `tempC?` / `powerW?` / `fanRpm?` / `fanPct?` | CPU 温度 / 封装功耗 / 风扇转速 / 风扇占空比（转速读不到时设备端显示占空比），读不到就没有 |
| `mem` | `usagePct` / `usedBytes` / `totalBytes` | 物理内存占用与容量。「可用」不单推：`totalBytes − usedBytes` 即精确值（与 PC 端 available 同口径） |
| `gpu` | `name` | 主卡型号（数字属于这块卡）；显存总量在静态信息消息（schema 3）里 |
| | `usagePct?` / `memPct?` / `tempC?` / `powerW?` / `fanRpm?` / `fanPct?` | 占用 / 显存占用 / 温度 / 功耗 / 风扇转速 / 风扇占空比（笔记本独显常见只有占空比） |
| `bat` | `pct?` | 电量百分比 |
| | `charging` / `acOnline` | 是否充电中 / 是否接着适配器 |
| | `rateW?` | 电池功率（W，**正数**）：充电 = 充入功率，放电 = 放电功率，方向看 `charging`；**已接入但未充电**（满电续充 / 养护模式）如实给 `0`（与 PC 电源卡同口径） |
| | `secondsToEmpty?` / `secondsToFull?` | 剩余续航 / 充满还需（秒）：方向决定只有其一，未知则都缺席 |
| `net` | `downBps` / `upBps` | 全网卡合计下行 / 上行速率（**字节**/秒） |
| | `totalReceivedMiB?` / `totalTransmittedMiB?` | 开机以来累计收 / 发（**MiB 取整**——字节计数有 13~15 位，BLE 按字节计费）。旧版 PC 端没有这两个字段 |
| `disk` | `readBps` / `writeBps` | 全部卷合计读 / 写速率（**字节**/秒）；逐卷容量在静态信息消息里 |
| `cores` | `load` | 每核占用数组（**0~100 整数**，元素序 = 逻辑核序；BLE 按字节计费故取整）。首拍等场景可能是空数组之外——整组缺席（等价于未勾选） |
| `procs` | `list` | 进程榜（**按 CPU 排序 top 5**）：`name`（截 16 字符）、`cpuPct`（1 位小数）、`memMiB`（整数 MiB）。内存榜设备端按 `memMiB` 重排同一条列表即可 |

`cores` / `procs` 是移动端布局功能引入的**可选组**，默认不勾选——存量设备
的载荷一个字节都不变；两份都想要的设备按「组缺席 = 未勾选」处理。

浮点统一保留 1 位小数。速率单位是字节每秒（Bps），不是比特（bps）——乘 8 才是
bit/s。

## 布局消息（schema 2，独立于每拍载荷）

PC 端「编辑布局」为手机 / 平板**各存两份布局**（`flow` 流式瀑布 / `grid` 固定一屏），
但每个设备形态**只下发当前激活的那一份**，所以仍是**两种形态各一条**。PC 端无法
感知连上来的是哪种设备（协议只出不进），因此**两条都发、设备端自己挑**。它是
**一次性消息**，不进每拍载荷：

```json
{"schema":2,"type":"layout","device":"phone","mode":"flow","cols":4,"rowUnit":92,
 "widgets":[{"type":"cpu","x":0,"y":0,"w":2,"h":3},{"type":"mem","x":2,"y":0,"w":2,"h":3}]}
{"schema":2,"type":"layout","device":"phone","mode":"grid","cols":4,"rows":4,"rowUnit":92,
 "widgets":[{"type":"cpu","x":0,"y":0,"w":1,"h":2},{"type":"mem","x":1,"y":0,"w":1,"h":2}]}
{"schema":2,"type":"layout","device":"pad","mode":"grid","cols":6,"rows":6,"rowUnit":92,
 "widgets":[{"type":"cpu","x":0,"y":0,"w":2,"h":2},{"type":"mem","x":2,"y":0,"w":2,"h":2}]}
```

| 字段 | 说明 |
| --- | --- |
| `schema` | 恒为 `2`（与每拍载荷的 `1` 区分；旧设备端解析 schema 1 时对它直接忽略即可） |
| `type` | 恒为 `"layout"` |
| `device` | 设备形态：`"phone"`（4 列）或 `"pad"`（6 列）。**缺席视为 phone**（只认单布局的旧 PC 端发的就是不带 device 的那条） |
| `mode` | `"flow"`（流式瀑布）或 `"grid"`（固定一屏）。**缺席 / 未知值一律按 flow**（固定一屏是新能力，必须显式下发；旧 PC 端的消息都是流式语义） |
| `cols` | 网格列数（手机 4 / 平板 6；设备端按它换算卡宽，不要写死） |
| `rows` | **仅 grid**：一屏的行数（手机 4 / 平板 6）。设备端把可用高度按 rows 等分；flow 不下发该字段（即使有也忽略） |
| `rowUnit` | 行单元（逻辑像素，当前 92），**仅 flow / 旧消息兜底**：旧设备端按它算 `h × rowUnit`。新 grid 用 `rows` 百分比，不依赖它；flow 的 `h` 已不表示物理高度 |
| `widgets[].type` | 组件类型，共 11 种：`cpu` `mem` `bat` `gpu` `power` `net` `trend` `cores` `disk` `procCpu` `procMem`（每种至多一个实例，两种形态共用同一套白名单） |
| `widgets[].x` / `y` | 网格坐标（格）。**flow**：(y,x) 只决定阅读顺序（消息已按 (y,x) 排好），设备端按数组顺序流式排列；**grid**：`left = x/cols`、`top = y/rows`，绝对定位到一屏内 |
| `widgets[].w` | 宽度（跨 `w` 列）：两种模式都是卡宽 = `w/cols` 的百分比，减去固定 px 边距画间隙 |
| `widgets[].h` | **flow**：不表示物理高度，只保留语义 `h < 3` = 精简卡（只留大数字 / 环）、`h ≥ 3` = 详细卡（含明细行）；**grid**：卡高 = `h/rows` 的百分比（跨 `h` 行），同时保留同一套精简 / 详细语义 |

**两种模式的设备端渲染**：

- **flow（流式瀑布）**：卡片按 `widgets` 数组顺序依次排列、一行放不下就换行，
  宽度 = `w/cols`，**高度由内容决定**（整页可滚动）。同一行内卡片顶对齐，行高取
  该行最高的一张——PC 端「流式预览」与 App 是同一套效果。
- **grid（固定一屏）**：像手机桌面摆小组件，整块棋盘**严格铺满一屏**（面板等
  PC 端之外的页面元素之外），不滚动。设备端把棋盘可用高度按 `rows` 等分，卡片
  `left = x/cols`、`top = y/rows`、`width = w/cols`、`height = h/rows`（都是百分比）。
  PC 端编辑时保证同一屏内不重叠、不越界；设备端按坐标还原即可。

**触发时机**：连接建立后两条必达（先于或伴随首拍，均有可能；连接后最先到的
其实是静态信息消息，见下一节）；PC 端每次保存布局或**切换任一设备的激活模式**，
**两条一起全量重发**。发送顺序固定**先 pad 后 phone**——不认 `device` 字段的旧版
App 两条都会应用、后者覆盖前者，最终停在 phone，与单布局时代行为一致。`widgets`
为空数组是合法布局（用户把组件全删了）。

**兼容性**（两端各自成立，不要求同时升级）：

- 新设备端 + 旧 PC 端（消息无 `mode`）→ 按 **flow** 渲染，也就是旧版「按坐标绝对
  定位」的观感不再保留，改为流式——这是新 App 的既定语义；
- 旧设备端 + 新 PC 端（不认 `mode` / `rows`）→ 仍按 `x/cols` + `y×rowUnit` 绝对定位；
  对 flow 消息会得到「坐标错位但能显示」的旧观感，对 grid 消息因 `y×rowUnit` 可能
  超出预想高度，属已知降级。升级 App 即可获得两种模式的正确渲染。

**帧格式**与每拍载荷完全一致：裸 TCP 一行 NDJSON、WebSocket 一条 text 消息、
BLE 同一套 20 字节分帧。每条消息全 11 种组件约 570 字节（grid 只多一个 `rows`
字段），**各自**在 BLE 64 帧（≈1152 字节）重组预算内（两条不合包，体积闸门各管各的）。

> DIY 屏等只关心每拍载荷的设备：按行的裸 TCP / 按消息的 WS 会多出这些
> schema≠1 的行/消息，**跳过不认识的 schema 即可**，不要按行号对位。

> BLE 通道容量有限且不排队：两条布局消息背靠背推送时，若与一拍载荷挤在
> 一起可能被丢弃其中一条。设备端应**按 device 独立持久化**收到的布局消息原文
> （含 `mode`，下次启动直接回填、下次 PC 端编辑时两条都会重发），丢弃一条不会
> 有持久影响。模式切换（PC 端改 flow/grid）也是一次「两条一起重发」，App 按
> 收到的 `mode` 重新渲染即可——本端不提供模式开关。

## 静态信息消息（schema 3，独立于每拍载荷）

CPU 型号、逐卷磁盘容量这类**慢变数据**单独一条消息下发——它们是「移动端卡片
与 PC 主面板对齐」要用的，但每拍载荷的 1KB（BLE 预算）装不下，也不值得拍拍
重发：

```json
{"schema":3,"type":"info",
 "cpu":{"brand":"12th Gen Intel(R) Core(TM) i7-12700H","physicalCores":14,"logicalCores":20},
 "gpu":{"memTotalBytes":6442450944,"others":["Intel(R) Iris(R) Xe"]},
 "bat":{"remainingWh":67,"fullChargeWh":82},
 "disk":{"volumes":[{"mount":"C:\\","pct":83,"usedGiB":775,"totalGiB":932}]}}
```

| 字段 | 说明 |
| --- | --- |
| `schema` | 恒为 `3`（只关心每拍载荷的设备端按「不认识的 schema 忽略」处理） |
| `type` | 恒为 `"info"` |
| `cpu?` | `brand`（截 36 字符）/ `physicalCores` / `logicalCores`——勾选 cpu 组才有 |
| `gpu?` | `memTotalBytes?` 主卡显存总量（byte，拿不到则缺席；显存已用 = 总量 × 每拍 `gpu.memPct`）；`others` 主卡之外的设备名（≤2 个，各截 16 字符，**不带占用%**——那是每拍数据，预算装不下） |
| `bat?` | `remainingWh` / `fullChargeWh`——**整数 Wh**（整数量级让「内容变了」极少触发重发） |
| `disk?` | `volumes[]`：`mount`（截 16 字符）、`pct`（整数百分比）、`usedGiB` / `totalGiB`（整数 GiB）。按挂载点排序、最多 4 卷；**逐卷读写速率不在此**（用每拍 `disk` 的合计速率） |

组同样跟随 PC 端勾选（没勾 cpu 组就没有 `cpu` 对象）；四个对象都缺席时是一条
只有 `{"schema":3,"type":"info"}` 的合法空消息。

**触发时机**：连接建立后必达，且**先于两条布局消息**（设备端先拿到型号 /
逐卷容量，随后渲染布局卡片才不缺行）；PC 端检测到内容变化时重发（brand /
核心数 / GiB / 整数 Wh 都是慢变量，正常运行几乎不触发）；另有约 60 拍一次的
**心跳重发**——BLE 连接突发时容量有限的通道可能无声丢掉这条，它不像布局消息
有「PC 端每次编辑都重发」的自愈路径，靠周期重发兜底。

**帧格式**与每拍载荷、布局消息完全一致（NDJSON 一行 / WS 一条 text / BLE 同一套
20 字节分帧），全量约 300~400 字节。设备端应**持久化**收到的静态信息（下次启动
直接回填）；旧版 PC 端不发这条，相关明细行（型号 / 核心数 / 容量 Wh / 逐卷面板）
按缺席隐藏即可，不要假定它必在。

## 节拍与节流

- 推送间隔由 PC 侧用户设置，设备端无法协商；按 `tsMs` 的新旧判断数据是否活着即可；
- 同一时刻 PC 侧可能一个客户端都没有——连上后第一拍立刻到，无需等一个间隔
  （裸 TCP 因协议判定窗口最多延后 ~250 ms，WebSocket 握手毫秒级通过）；
- BLE 侧若设备处理不过来（通道满），PC 会**丢弃该拍**而不是排队——
  设备端按「有新拍就覆盖旧拍」处理最稳。
