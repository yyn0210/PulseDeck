# PulseDeck 数据推送协议（v1）

> 面向设备端作者：DIY 小屏（ESP32 / Arduino）、手机 / 平板 App、树莓派状态屏等，
> 如何接入 PulseDeck 的监控指标推送。协议实现以 `src-tauri/src/push/` 为准，
> 本文档是它的人话版。

## 一句话概览

PulseDeck 在本机开两条**只读单向**的通道（TCP——同一端口同时收裸 TCP 与
WebSocket 客户端，以及 BLE 串口），按用户设置的推送间隔
（300 ms ~ 10 s，默认 1 s）持续吐出同一份紧凑 JSON：

```json
{"schema":1,"tsMs":1760700000000,"sampleIntervalMs":1000,"host":"desktop",
 "cpu":{"usagePct":23.5,"freqMhz":2900,"freqLive":true,"tempC":61.5,"powerW":12.3},
 "mem":{"usagePct":58.3,"usedBytes":9500000000,"totalBytes":17000000000},
 "gpu":{"name":"NVIDIA GeForce RTX 3060 Laptop GPU","usagePct":37,"memPct":44,"tempC":66,"powerW":75.5},
 "bat":{"pct":82,"charging":true,"acOnline":true,"rateW":45.2},
 "net":{"downBps":1234567,"upBps":98765},
 "disk":{"readBps":300000,"writeBps":1200000}}
```

设备**无法**向 PulseDeck 发送任何指令——两条通道都不解析外来字节。没有鉴权：
TCP 只应在可信局域网内开放。

## TCP 通道（NDJSON 与 WebSocket 同端口）

TCP 通道在**同一个端口**（默认 `17432`）上同时收两种客户端：服务端在连接后
约 250 ms 的判定窗口内看首字节——是 HTTP 请求行就走 WebSocket 握手，否则按
裸 TCP（NDJSON）对待。两种客户端收到的 JSON 完全相同，只是帧格式不同。

### 裸 TCP（NDJSON）

1. 在 PulseDeck 设置页「数据推送」里开启 TCP，记下状态行显示的 `局域网IP:端口`
   （默认端口 `17432`）；
2. 设备作为客户端连上去，**连接成功即收到一拍**，之后每个推送间隔收到一拍
   （首拍会因协议判定窗口最多延后 ~250 ms）；
3. 帧格式是 NDJSON：每拍一行 UTF-8 JSON，以 `\n` 结尾；
4. 掉线自动重连即可；服务端从不主动断开空闲连接，但**读取极慢的客户端**
   （写缓冲 1 秒推不下去）会被服务端剔除；
5. 客户端连上后**保持静默**——本协议只收不发，发了的内容也不会被解析。

Python 验收示例：

```python
import socket, json
s = socket.create_connection(("192.168.1.100", 17432))
buf = b""
while True:
    buf += s.recv(4096)
    while b"\n" in buf:
        line, buf = buf.split(b"\n", 1)
        if line.strip():
            d = json.loads(line)
            print(d["cpu"]["usagePct"], d.get("mem", {}).get("usagePct"))
```

### WebSocket

浏览器 / 手机网页**不需要任何原生 App**，一个页面直连：

```js
function connect() {
  const ws = new WebSocket("ws://192.168.1.100:17432/");
  ws.onmessage = (e) => {
    const d = JSON.parse(e.data);   // 与 NDJSON 同一份 JSON（无换行）
    console.log(d.cpu?.usagePct, d.mem?.usagePct);
  };
  ws.onclose = () => setTimeout(connect, 1000); // 慢消费者会被断开，务必重连
}
connect();
```

| 项 | 值 |
| --- | --- |
| URL | `ws://<局域网IP>:17432/`（路径忽略、无子协议；`wss://` 不支持——面向可信局域网） |
| 消息格式 | 每拍**一条 text 消息**，内容 = 同一份 JSON（不带换行） |
| 心跳 | 客户端可发 Ping 帧，服务端自动回 Pong（内容不解析） |
| 断开条件 | 写超时 1 s / 队列积压约 8 拍未消费 / 对端关闭——客户端做好重连即可 |

> WebSocket 与裸 TCP 共用防火墙授权：Windows 首次开启 TCP 弹的授权提示，
> 对两种客户端一视同仁。

> **在哪跑这段代码有讲究**：别在浏览器内部页（`chrome://` / `edge://` 开头，
> 如新标签页、设置页）或带严格 CSP 的网站控制台里执行——那些页面自身的
> `connect-src` 策略会在连接发出前就拦截（报错 "violates the following Content
> Security Policy directive"），与推送服务无关。地址栏打开 `about:blank` 后再开
> 控制台即可；或者直接用仓库自带的验收页 [`tools/push-viewer.html`](../tools/push-viewer.html)
> ——双击用浏览器打开（`file://` 页面没有 CSP 限制），改好地址点「连接」，
> 指标卡片 / 原始 JSON / 断线自动重连都是现成的。

## BLE 通道（Nordic UART Service）

PulseDeck 以标准 NUS 服务广播，广播名 `PulseDeck`。用任何 BLE 串口客户端
（nRF Connect、SerialBluetoothTerminal、ESP32 NimBLE……）连接并**订阅 TX 特征的
notify**，即可收到分帧的数据流。

| 项 | 值 |
| --- | --- |
| 服务 UUID | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| RX 特征（设备→PC，write） | `6e400002-b5a3-f393-e0a9-e50e24dcca9e`（内容被忽略） |
| TX 特征（PC→设备，notify） | `6e400003-b5a3-f393-e0a9-e50e24dcca9e`（数据流） |

### 20 字节安全帧

协商 MTU 在各平台都拿不到，所以按最保守的 20 字节切帧。每帧格式：

```text
[0] idx    本帧序号，0 起
[1] total  本拍载荷共几帧
[2..] data ≤18 字节的载荷切片
```

设备端重组算法（Rust 参考实现在 `push::ble_reassemble`）：

```text
按 total 开一个槽位数组；每收到一帧，校验 idx < total 且帧头的 total 一致，
放进对应槽位；全部槽位填满后按序拼接，得到一拍完整的 UTF-8 JSON，按行解析即可
（BLE 载荷本身不含换行）。任何一帧校验失败就丢弃整拍，等下一拍——
每一拍都自带 (idx, total)，没有跨拍状态。
```

一拍全组载荷约 300~500 字节（≈ 20 帧），1 Hz 下 BLE 完全吃得下；推送间隔低于
500 ms 时建议减少勾选的指标组。

## 载荷字段（schema 1）

顶层：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schema` | int | 协议版本，当前恒为 `1`；不认识就别解析 |
| `tsMs` | int | **快照采样时刻**（Unix 毫秒）——是数据年龄，不是设备收到它的时刻 |
| `sampleIntervalMs` | int | 快照的实测采样间隔（毫秒） |
| `host` | string? | 主机名（多台电脑时用于标注），缺省=未取到 |

六个指标组**按用户勾选出现**，未勾选的组整组缺席；机器上没有的组也缺席
（无 GPU 不出 `gpu`、无电池不出 `bat`）。组内读不到的字段同样省略（键不存在），
不要假定任何字段必在。

| 组 | 字段 | 说明 |
| --- | --- | --- |
| `cpu` | `usagePct` | 总占用（%，忙时口径，与任务管理器一致） |
| | `freqMhz` | 主频（MHz）。注意键名是 `freqMhz`（serde camelCase，非 `freqMHz`） |
| | `freqLive` | `true` = 实时主频；`false` = 该平台只能给标称频率（基准值） |
| | `tempC?` / `powerW?` / `fanRpm?` | CPU 温度 / 封装功耗 / 风扇转速，读不到就没有 |
| `mem` | `usagePct` / `usedBytes` / `totalBytes` | 物理内存占用与容量 |
| `gpu` | `name` | 主卡型号（数字属于这块卡） |
| | `usagePct?` / `memPct?` / `tempC?` / `powerW?` / `fanRpm?` | 占用 / 显存占用 / 温度 / 功耗 / 风扇 |
| `bat` | `pct?` | 电量百分比 |
| | `charging` / `acOnline` | 是否充电中 / 是否接着适配器 |
| | `rateW?` | 电池功率（W，**正数**）：充电 = 充入功率，放电 = 放电功率，方向看 `charging` |
| `net` | `downBps` / `upBps` | 全网卡合计下行 / 上行速率（**字节**/秒） |
| `disk` | `readBps` / `writeBps` | 全部卷合计读 / 写速率（**字节**/秒） |

浮点统一保留 1 位小数。速率单位是字节每秒（Bps），不是比特（bps）——乘 8 才是
bit/s。

## 节拍与节流

- 推送间隔由 PC 侧用户设置，设备端无法协商；按 `tsMs` 的新旧判断数据是否活着即可；
- 同一时刻 PC 侧可能一个客户端都没有——连上后第一拍立刻到，无需等一个间隔
  （裸 TCP 因协议判定窗口最多延后 ~250 ms，WebSocket 握手毫秒级通过）；
- BLE 侧若设备处理不过来（通道满），PC 会**丢弃该拍**而不是排队——
  设备端按「有新拍就覆盖旧拍」处理最稳。
